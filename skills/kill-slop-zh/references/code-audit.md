# 结合源码的界面审查

源码搜索只提供线索，不提供结论。正则命中、颜色 token、组件外形或常见短语，都不能单独证明界面模板化，也不能直接授权修改。

## 1. 确认范围

确认需要审查的应用、包、路由或组件集合。如果仓库包含多个面向不同受众的产品，先明确目标，不无差别扫描整个仓库。

默认排除依赖、构建产物、锁文件、压缩文件和版本控制内部文件，除非用户明确要求包含。不要读取密钥或凭据。

## 2. 搜索源码

使用项目已有的搜索工具寻找重复出现的设计与文案信号，包括：

- 重复渐变、发光、阴影、圆角、颜色和动画声明。
- 共享卡片容器、嵌套面板、图标容器、徽章、胶囊和区块标签。
- 重复标题、含糊操作、占位文案和无来源指标。
- 绕过现有 token 或组件的硬编码值。
- 缺失的空状态、加载、错误、焦点、禁用和移动端状态。
- 在主界面之前加载的大型依赖或第三方脚本。

独立扫描器不是必需品。优先使用项目已有工具，不要为了生成更长的报告而安装扫描器。

## 3. 结合语境复核

对每个候选项，阅读周边组件、样式、内容和项目规范，并区分：

- **确认问题**：有具体证据说明它损害理解、一致性、任务完成、可访问性或性能。
- **有意设计**：品牌 token、刻意选择的插画、有意义的状态色、行业表达或用户明确要求的效果。
- **需要确认方向**：会改变品牌、受众、产品行为或受保护内容的选择，应带着推荐方案提问。

不要根据搜索结果批量修改。审查模式只报告；改造模式可以直接修复确认问题，涉及方向或受保护行为时再询问。

## 4. 在正确层级修复

- 优先修改共享 token、基础组件和内容来源，而不是重复局部补丁。
- 保持 diff 聚焦且容易审查，不格式化无关代码。
- 不碰他人正在进行的工作和不熟悉的用户修改。
- 除非用户要求或有明确证据，不更改现有品牌颜色和产品行为。
- 不为了让修复看起来完整而发明新色板、指标、状态、功能或依赖。
- 先删除重复，再考虑新增抽象；没有证据时不为一次性变体创建共享组件。

## 5. 验证结果

修改后重新执行定向搜索，区分已解决问题和有意保留的模式。命中数量下降本身不代表成功。

运行项目相关的类型、lint、构建和测试命令。能够运行界面时，检查真实桌面和移动端行为，包括主要任务、键盘操作、减少动态效果、加载、空状态和错误状态。报告保留的候选项与未验证范围。
